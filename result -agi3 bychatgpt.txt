사용할 수 있습니다. 가장 유망한 이식 대상은 문제 해결 코드를 실행하는 하네스, 특히 비동기 작업 처리와 캐시를 고려한 계산량 배분입니다. AGI-3 게임 솔버 전체를 AGI-2에 그대로 붙이는 방식은 맞지 않습니다.

기존 프로젝트와 비교하면 차이가 더 분명합니다. old/v60-repaired-instrumented.ipynb에는 이미 지속 Python 샌드박스, 객체 비교, 격자 차이, 단계별 오류 피드백이 있습니다. 이것들을 AGI-3에서 처음 가져오는 것처럼 새로 만들 필요는 없습니다. 실제로 추가할 가치가 큰 부분은 다음 순서입니다.

첫째, 28개 생성 요청이 모두 끝나기를 기다리는 락스텝 루프를, 완료된 문제부터 도구 실행과 다음 생성을 이어가는 비동기 방식으로 바꾸는 것입니다.
둘째, 활성 문제 수를 KV/재귀 상태 캐시 용량에 맞추고, 한 문제의 연속 작업이 캐시를 재사용하게 하는 것입니다.
셋째, 실패 가설과 검증된 코드를 재개 시점까지 보존해 같은 추론·코드 작성을 반복하지 않게 하는 것입니다.
넷째, 기존 객체 분석이 놓치는 사례에만 새 객체 대응·회전 분석을 선택적으로 추가하는 것입니다.

점수 상승은 아직 미측정입니다. 이 자료로 7.36이 몇 점까지 오른다고 환산할 수 없습니다. 다만 단순한 아이디어 글이 아니라 실제 패치와 실행 로그가 있어, 무엇을 이식하고 시험할지 구체적으로 정할 수 있습니다.

3. 옮길 수 있는 것과 없는 것

가. 비동기 실행과 활성 작업 수 제한: 가장 유망합니다.

새 하네스는 많은 게임 세션을 대기 상태로 두되, 실제 활성 스트림을 10개로 제한합니다. 도구 실행 후에도 같은 게임이 슬롯을 유지해 캐시를 재사용하며, 컨텍스트를 크게 비우는 시점을 작업 교체 기회로 활용합니다.

로컬 v60의 run loop는 QENG.gen으로 활성 문제 전체를 생성한 다음, 도구 실행 전체가 끝나야 다음 라운드로 갑니다. 생성이 빨리 끝난 문제도 다른 문제를 기다립니다. 새 하네스의 아이디어는 이 대기를 줄일 수 있습니다. 다만 서버가 이미 배치 내부 디코드를 효율적으로 처리할 수 있으므로, 락스텝 제거만으로 처리량이 몇 배 오른다고 보장할 수는 없습니다.

이식안:
문제별 상태 객체를 유지하고, 비동기 서버 또는 비동기 엔진에 개별 요청을 넣습니다. 완료 즉시 해당 문제의 코드를 검증하고 다음 요청을 준비합니다. GPU 요청 수와 CPU 검증 워커 수는 별도로 제한합니다. 전체 마감과 제출 파일 저장은 한 곳에서 관리합니다.

10이나 28을 정답으로 고정하면 안 됩니다. 실제 모델과 하드웨어에서 active=8/16/28 등 소수 후보를 시험하고, 실제 prompt 길이·캐시 적중·선점·집계 처리량·완료 후보 수로 고르십시오. 라이브러리 호출을 여러 Python 스레드로 감싸는 것만으로 안전한 비동기 엔진이 되지는 않습니다.

나. 계산량 재배분: 원리는 좋지만 점수 공식은 재작성해야 합니다.

AGI-3 priority_value는 현재 레벨, 행동 횟수, 토큰, 남은 레벨 가치에 의존합니다. 여기의 레벨 완료는 환경이 제공하는 실제 성공 피드백입니다. 반면 AGI-2의 train 전쌍 통과는 숨겨진 test 정답을 보증하지 않습니다. 따라서 AGI-3의 level을 pairs_ok로 치환하면 train 과적합 문제에 예산을 몰아줄 수 있습니다.

AGI-2에서는 모든 문제에 최소 탐색 기회를 준 뒤, 새로운 train 통과 후보가 생기는 속도, 오류 감소, 후보 간 예측 차이, 중복 반복, 추가 비용을 이용해 다음 작업을 고르는 형태가 낫습니다. 이 신호들도 정답 확률 자체는 아닙니다. 개발 태스크에서 보정하고 별도 홀드아웃에서 확인해야 합니다.

캐시가 남은 작업을 우대하되 한 문제의 독점을 막는 작업량 상한과 대기시간 보상을 두십시오. AGI-3 원본의 장시간 슬롯 유지 정책은 레벨 진행이 없는 AGI-2에서 그대로 쓰면 일부 문제를 오래 굶길 수 있습니다. 마감 직전에는 새로운 장기 탐색보다 유효 후보 검증과 두 슬롯 확정을 우선하십시오.

다. 함수 유지: 기존 기능과 겹치며, 재개·재시작 보완에 유용합니다.

새 retained_functions.py는 함수 소스를 검사해 복원합니다. 일반 변수까지 저장하는 방식이 아닙니다. 변화하는 격자는 인자로 받게 하고, 사라진 전역 변수에 의존하는 함수는 거부합니다.

현재 로컬 v60은 이미 문제별 지속 namespace가 있어 같은 패스의 함수 재사용은 됩니다. 추가로 유용한 부분은 P2 재개 또는 워커 재시작입니다. reopen_messages는 새 샌드박스에서 solve를 다시 정의하도록 안내합니다. 이때 검증된 helper와 후보 코드를 소스·해시·검증 결과와 함께 복원하면 반복 생성을 줄일 수 있습니다.

문제별 함수 저장소와 여러 문제에 공용인 도구를 구분하십시오. 한 문제에서 만든 위치·색 상수가 다른 문제로 전파되지 않게 해야 합니다. 함수 소스 보존은 코드 실행 격리 자체를 대신하지 않습니다.

라. 객체 단위 차이 분석: 보완재로 유용하지만 그대로는 안 됩니다.

새 frame_diff는 객체를 대응시켜 이동·회전·생성·소멸·색 변경·크기 변경을 요약합니다. 같은 형태의 여러 객체 대응에는 최소 비용 매칭을 사용합니다. segmentation 패치는 회전 정규화와 색에 독립적인 기준 방향을 다룹니다.

AGI-2에서는 두 곳에 응용할 수 있습니다.
1) train 입력과 정답 출력 사이의 변환 후보 요약
2) solve의 train 예측과 정답 사이의 실패 원인 요약

그러나 기존 v60에도 task_report의 객체 매칭, D4, diff_cells, 색 대응, check의 단계별 피드백이 있습니다. 새 요약을 무조건 덧붙이면 프롬프트만 길어질 수 있습니다. 기존 분석이 틀리거나 모호한 사례를 모아 보완 효과를 비교해야 합니다.

중요한 이식 제약을 CPU에서 재현했습니다. 원본 compute_frame_diff는 같은 크기 격자를 전제로 zip으로 순회합니다. [[1]]과 [[1,2]]를 비교하면 changed_cell_count=0을 반환합니다. 원래 용도의 전제 위반이지 AGI-3에서 곧바로 버그라는 뜻은 아닙니다. 하지만 크롭·확대·조립이 많은 AGI-2에 그대로 넣으면 위험합니다.

AGI-2 래퍼는 크기를 먼저 검사하고, 크기가 다르면 shape_changed와 크롭/스케일/좌표 정렬 가설을 별도로 처리해야 합니다. 임의 패딩이 올바른 대응을 증명하지는 않습니다. 1:1 객체 매칭도 복제, 분할, 합체를 완전히 표현하지 못합니다. 여러 객체 분할 방식과 다대일·일대다 후보를 유지하고 “확정 사실” 대신 대응 가설로 제공하십시오. 새 회전 정규화는 반사를 아직 포함하지 않으므로 기존 D4 기능을 대체하면 오히려 퇴보할 수 있습니다.

마. 사고 기록 보존과 컨텍스트 정리: 비교 실험 가치가 있습니다.

새 설정은 reasoning_content를 보존하고, 서버 템플릿에도 preserve_thinking=true를 전달합니다. 저자는 사고 기록을 제거하면 성능이 낮아졌다고 설명합니다. 이는 현재 경로의 no-think 서술 증류가 반드시 최선이라는 증거가 없다는 점을 상기시킵니다. 반대로 AGI-3 결과만으로 AGI-2에서도 모든 사고를 보존해야 한다는 결론 역시 나오지 않습니다.

AGI-2용 비교군은 다음처럼 작게 시작하는 편이 좋습니다.
- 현행: 사고 제거
- 대안1: 최근 한 턴 사고 보존
- 대안2: 실패 가설, 반례, 검증된 함수, 미결 조건만 구조화해 보존

동일 시간에서 정답과 중복 가설률을 비교하십시오. 128K 컨텍스트를 바로 도입할 필요는 없습니다. 이력 삭제 시 조금씩 반복해서 지우는 대신 여유를 확보하는 원리는 유용하지만, 처음의 task 예제와 검증 결과까지 잃지 않도록 해야 합니다. 실제 trim이 거의 없는 짧은 실행이라면 이 최적화의 효과도 작습니다.

바. 무효 동작 방지: 후보 중복과 코드 버전 관리로 번역할 수 있습니다.

AGI-3는 행동 후 내부 보드가 바뀌지 않으면 같은 배치의 후속 행동을 중단합니다. AGI-2에서는 동일 코드와 동일 입력을 재검증하거나, 동일 예측을 반복 제출하는 비용을 줄이는 것으로 옮길 수 있습니다. 결과에는 후보 ID, 코드 해시, train 예제 ID를 붙여 옛 실패 피드백이 새 코드 결과로 오인되지 않게 하십시오.

단, 동일 train 예측을 내는 서로 다른 규칙을 모두 제거하면 안 됩니다. test에서는 달라질 수 있습니다. 실행 캐시는 동일 코드·동일 입력 기준, 최종 슬롯 중복 제거는 테스트 입력별 동일 출력 기준으로 구분하십시오. 동일 정답 행렬이어도 다른 실패 근거를 얻는 유효한 재검증까지 막지 않도록 해야 합니다.

사. 애니메이션, UNDO, 게임 오버 안내: 직접 이식 대상이 아닙니다.

AGI-2에는 게임 행동으로 새로운 환경 상태를 관측하거나, test 정답의 피드백을 받는 경로가 없습니다. ACTION7/UNDO, 사망 프레임, 예산 막대, 레벨 이전 지식은 그대로 쓸 수 없습니다. 코드 후보의 되돌리기나 train 반례 실험으로 의미를 바꿔야 합니다.

AGI-2의 여러 train 쌍은 한 게임의 연속 레벨도 아닙니다. 공유 규칙을 모든 쌍에서 동시에 확인해야 하며, 앞 예제에서 정한 상수나 해석을 뒤 예제에 무조건 전파하면 안 됩니다. 원본의 테두리 4칸 제외 역시 작은 AGI-2 격자에 적용해서는 안 됩니다.

아. 시각 입력과 모델 교체: 별도 실험입니다.

10배 확대 이미지와 diff 이미지는 멀티모달 모델이 작은 게임 화면을 읽도록 돕는 방법입니다. AGI-2 숫자 격자에 같은 확대를 적용한다고 새로운 정보가 생기지는 않습니다. 색상 격자 이미지를 추가하는 실험은 가능하지만 vision 지원 모델·프로세서·이미지 토큰 예산이 필요합니다. 텍스트 전용 설정과 혼동하지 마십시오.

Flash-Next 교체와 MTP, FP8 KV, SGLang 패치도 실행 구조 이식과 분리해야 합니다. 첨부의 594.25 tokens/s는 RTX PRO 6000, 해당 양자화 모델, 긴 컨텍스트, 해당 배치의 결과입니다. L4 네 장의 총 VRAM을 더해 같은 속도나 적재 가능성을 주장할 수 없습니다. PLE 호스트 RAM, TP 지원, GPU별 커널, 모델/draft 메모리를 따로 확인해야 합니다.

특히 Mamba/선형 어텐션 계열은 KV 여유뿐 아니라 재귀 상태 체크포인트 재사용도 중요하다는 것이 이 자료의 교훈입니다. 현재 27B/vLLM의 버전과 캐시 구현에서 무엇이 해당되는지 먼저 계측해야 합니다. SGLang 포크의 패치를 다른 엔진에 그대로 복사할 수는 없습니다.

4. 추천하는 최소 이식 설계

기존 흐름:
활성 문제 28개 → 전체 생성 완료 대기 → 전체 코드 실행 완료 대기 → 다음 라운드

제안 흐름:
문제 대기열 → 제한된 활성 요청 → 각 문제의 생성 완료 즉시 검증 → 후보/오류 기록 → 같은 문제 계속 또는 대기열 복귀 → 최종 두 슬롯

문제 상태에는 train 피드백만 저장하고, 평가용 test 정답은 의사결정 경로에서 분리합니다. 최종 후보는 현재 규칙·27B·4B 후보 저장소와 합칠 수 있습니다. AGI-3 실행 구조가 4B TTT를 대체하는 것은 아닙니다. 비용 대비 추가 정답이 있는 경로에 예산을 배분하는 상위 하네스로 활용할 수 있습니다.

소형 파일럿의 권장 비교 순서는 다음과 같습니다.
A: 로컬 v60 기준선
B: 같은 모델·프롬프트·토큰 설정, 비동기 처리만 변경
C: B에 캐시를 고려한 활성 수 제한과 작업 유지 정책 추가
D: C에 재개 시 함수/실패 가설 복원 추가

객체 피드백과 새 모델은 별도 비교군으로 두십시오. 여러 기능을 한꺼번에 바꾸면 이득의 원인을 알 수 없습니다. 30~40개 개발 미사용 문제는 초기 선별용으로 활용하고, 차이가 작으면 더 넓은 평가에서 확인해야 합니다. 정답 수만 아니라 총 시간, 처리 문제 수, 고유 후보 수, prompt/생성 토큰, 실제 캐시 적중, 선점, CPU 검증 대기를 함께 기록하십시오.

첫 파일럿에서 비동기가 빨라지지 않으면 병목이 락스텝보다 GPU 디코드에 있는지 확인하고 해당 공사를 확대하지 않는 것이 좋습니다. 캐시가 거의 적중하지 않으면 프롬프트 안정성과 엔진 지원부터 보아야 합니다. 목표는 높은 tokens/s 자체가 아니라 정해진 시간 안의 최종 두 슬롯 정답 수입니다.

5. 이번에 수행한 검증과 한계

노트북의 소스와 텍스트 출력 로그를 추출했고, 새 패치 중 완전한 신규 Python 모듈 5개를 추출해 문법을 확인했습니다. frame_diff와 retained_functions의 작은 CPU 테스트도 실행했습니다.
- 동일 크기 격자에서 변경 셀 수 확인
- 다른 크기 격자의 추가 열을 놓치는 전제 위반 사례 확인
- 입력을 인자로 받는 helper 보존 확인
- 사라진 전역 격자에 의존하는 helper 거부 확인

경로: review/1005/check_transfer.py, review/1005/transfer_checks.json
저장 로그: review/1005/output_020.txt
대조한 기존 소스: review/1005/v60_reference.txt

게임 실행, GPU 모델 적재, AGI-2 정확도 실험은 수행하지 않았습니다. 로컬 v60 파일이 과거 공개 점수 7.36을 낸 제출물과 완전히 같은 파일인지도 이번에는 확인하지 않았습니다. 따라서 기존 기능 비교는 해당 로컬 파일을 기준으로 합니다. 원본 노트북과 프로젝트 실행 코드는 수정하지 않았습니다.
